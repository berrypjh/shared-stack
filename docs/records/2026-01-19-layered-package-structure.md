# 디자인 시스템을 토큰 · 공유 계약 · 플랫폼 UI 패키지로 나눠 시작

컴포넌트 모음이 아니라 오래 유지하고 넓힐 디자인 시스템을 전제로, 처음부터 패키지 경계를 나눔. 최종 구조는 `design-tokens → ui-core → react-ui · react-native-ui` 네 층.

## 상황

- 목표는 셋
  - **학습** — 라이브러리를 만들며 프론트엔드 패키지 구조와 디자인 시스템을 익힘
  - **AI 활용 실험** — 제작 과정에서 AI 를 어떻게 쓸지 시험함
  - **재사용** — 결과물을 실제로 필요한 사이트에 다시 씀
- 구조는 처음부터 완성되지 않음. 구현 · AI 실험 · 실제 사이트 적용을 거치며 패키지마다 책임이 분명해짐

## 판단

세 구조를 견주어 4개 층을 채택.

| 구조                                                   | 결과 | 이유                                                                                                                                 |
| ------------------------------------------------------ | ---- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 모놀리식 한 패키지                                     | 버림 | 초기 속도 · import 경로는 가장 단순함. 대신 web · native 분리를 계속 tree-shaking 에 기대고, 컴포넌트 하나만 고쳐도 전체 버전이 오름 |
| `design-tokens + react-ui + react-native-ui`           | 버림 | 공유 prop 계약을 react-ui 에 두면 react-native-ui 가 web 패키지에 기대 `react-dom` 이 의존 트리에 들어올 수 있음                     |
| `design-tokens → ui-core → react-ui · react-native-ui` | 채택 | 공유 계약은 ui-core, 렌더링은 플랫폼 패키지. 한쪽 앱에 다른 플랫폼 의존성이 섞이지 않음                                              |

react-ui 와 react-native-ui 는 겉 컴포넌트가 비슷해도 의존성과 렌더 대상이 다름. 둘은 나누되 prop API 는 같게 — 두 패키지가 ui-core 계약을 감쌈([기록](2026-01-30-ui-core-shared-contracts.md)). react-ui 안에 "플랫폼 중립 폴더"를 두는 방법도 있었지만 사실상 ui-core 를 폴더 경계로 만든 것.

**"같은 약속, 다른 구현"을 폴더가 아니라 패키지 경계로 표현함.** 장기적으로는 패키지 경계가 더 강한 규칙이라 봄.

## 반영

- 트레이드오프를 받아들임
  - **build 순서** — `design-tokens → ui-core → react-ui · react-native-ui`. Nx 의존 그래프가 순서를 처리함. 이 구조가 Nx 를 쓴 직접적인 이유 중 하나
  - **여러 패키지로 퍼지는 변경** — 토큰 카테고리 하나가 네 패키지를 함께 바꿀 수 있음. scope 별 Conventional Commits 로 어느 패키지에 무엇이 바뀌었는지 추적함
